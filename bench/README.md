# Benchmarks

iso8583tool is measured the way a user runs it, one process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds iso8583tool (with `CGO_ENABLED=0`, as the Makefile does), runs each command in interleaved rounds, and reports latency, CPU time and peak RSS.

```console
$ go install github.com/nao1215/himorime@latest
$ make bench            # himorime run bench
$ make bench-compare    # himorime compare --against main bench
```

## Regression suite: himorime.yaml

`make bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v0.8.1 make bench-compare` compares against another revision. `himorime run --filter 'view 124 fields' bench` measures one benchmark, and `himorime run --tag smoke bench` only the small messages.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

iso8583tool reads one message per call, so the size in a benchmark name is the number of data fields in the message: 10, where start-up dominates, and 124, every data field of the basei-starter spec at its largest length (about 35 KB packed), the largest message there is. The message documents are generated by `gen.sh` before measuring, so no fixture is added, and both revisions run the working tree's `gen.sh`; setup packs them with the iso8583tool being measured.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `iso8583tool version` | starting iso8583tool |
| `view 10 fields` | describe, `--format json`, `--filter 11` | unpacking, decoding and masking a small message |
| `view 124 fields` | describe, `--format json`, `--filter 55.9F02` | the same on every data field, including 20 EMV tags in field 55 |
| `diff 10 fields` | describe, `--format json` | comparing two small messages whose every value differs |
| `diff 124 fields` | describe, `--format json` | comparing every field and EMV tag of two full messages |
| `redact 10 fields` | JSON, `--format text` | writing a masked document of a small message |
| `redact 124 fields` | JSON, `--format text` | the same on every data field |
| `convert 10 fields` | JSON to hex, hex to JSON | packing a document and unpacking a message |
| `convert 124 fields` | JSON to hex, hex to JSON | the same on every data field |
| `validate 10 fields` | default, `--strict` | checking that a small message unpacks, and the per-MTI checks |
| `validate 124 fields` | default, `--strict` | the same on every data field |
| `validate error` | `--raw 01007220` | a message cut off after its bitmap, which fails with a hint, exit 1 |
| `doctor 10 fields` | `doctor` | unpacking a small message with every built-in preset |
| `doctor 124 fields` | `doctor` | the same on every data field |
| `send 10 fields` | `send --dry-run` | packing and framing a small document without sending it |
| `send 124 fields` | `send --dry-run` | the same on every data field |

`send` is measured with `--dry-run` only. A live round trip needs a server that answers every run, and a himorime hook cannot leave one running between runs; starting `e2e/mock` inside the measured command would measure the mock too. `specs` and `sample` print fixed lists and are not measured. The hex fields 52 (PIN data) and 64 (MAC) are left out of the generated messages because a value `convert` packs for them does not unpack to the same fields again.

Numbers from different machines are not comparable; compare revisions on one machine, as `make bench-compare` and CI do.
